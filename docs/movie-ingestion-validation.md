# 作品取り込みの検証

作品名をアプリのキーに変換する前に `validateSourceMovieTitles` を通す。

- T・ジョイ横浜／横浜ブルク13は、取得元の作品ID (`C…` / `E…`) と公式詳細ページ自身のIDを照合し、詳細ページの見出しを採用する。初回、予定表の表記が変わったとき、確認から30日経過したときに再確認する。予定表の省略表記を類似作品へ推測で結び付けない。
- 他の取得元は、空・HTML混入・プレースホルダー、同じ取得元IDの複数タイトル、前回からの作品名変更を検知する。初回の通常タイトルは `observed` として記録する。公式確認済みとは区別する。
- 正規化によって前後編や公開年などの異なるタイトルが同じキーになる場合は保留する。異なる映画の設定を勝手に統合しない。
- 保留された上映を含む日付は丸ごと更新を見送る。既存の上映と検索索引を保持し、`source_date_health` をエラーにする。正常な日付は更新する。
- `showings.source_movie_id` と `source_title` に取得元IDと表記を残す。確認結果は `source_movie_identity`、保留理由は `movie_ingestion_issues` に保存する。

## 公式サイトへのアクセス

通常の収集1回につき、詳細ページの新規確認は全映画館合計5リクエストまで。同じ作品を上映回ごとに取得しない。403・429や通信障害などが1映画館で1回起きたら、その映画館への追加の詳細確認を打ち切り、6時間は同じ表記を再確認しない。404・410のリンク切れはその作品だけを保留して24時間再確認しないため、後続作品の確認を妨げない。再試行や別経路への切り替えはしない。タイムアウト15秒・本文2MiB・固定ホスト・リダイレクト禁止で取得する。

確認済みの作品はD1に保存されるため、予算を使い切っても次回は未確認分から進む。キャッシュを読むだけでは確認日時を延長しない。導入時は現在上映中の作品をあらかじめ公式確認し、初回の確認待ちで全日程が更新保留になることを避ける。

## 保留の確認と解消

```sql
SELECT source_id, source_movie_id, observed_title, reason, evidence_url,
       first_seen_at, last_seen_at
FROM movie_ingestion_issues WHERE resolved_at IS NULL
ORDER BY last_seen_at DESC;
```

`detail_budget_exhausted` は次の通常収集、`detail_unavailable` / `detail_not_found` は `next_check_at` 以降の収集で再確認する。URL・ID・正式名を人が確認できた場合のみ、根拠付きの既存のタイトル補正カタログ／登録済みの作品情報を更新する。IDの再利用や実際の改題、キー衝突は予約・作品設定・旧URLの移行判断を伴うため、自動承認しない。後続収集で正常に確認できたら該当IDの問題を解決済みにする。上限を増やすことや、問題の行だけを削除して残りを公開することで回避しない。

## 制限

公式詳細との自動照合はT・ジョイ系2館から導入する。他館で初めて登場した、構文上正常だが誤っているタイトルは判別できない場合がある。他館の詳細ページ対応も、映画館側の安定した作品IDを確認してから追加する。現在の仕組みは全作品の内容の正しさを保証するものではない。

## 検証

`test/movie-identity.test.ts` で未知の短縮表記、ID不一致、応答サイズ制限、照合上限・失敗打切り・再開、キャッシュ期限、キー衝突、既存上映・検索索引の保持を確認する。`npm run ci:pr` とクリーンチェックアウトでの検証を実施する。

`existing_movie_key_change` は、正式名を採用すると公開済み作品のキーが変わることを示す。作品設定や共有URLの移行を確認するまではその日を更新しない。公式に同じ作品と確認できても、利用者の状態を無言で別キーへ切り離さない。

ローカル検証はGitHub Actionsと同じNode 22を使う。Node 26では現行のブラウザ通知テストが `localStorage` の組み込みグローバルの違いで失敗するため、Node 26での結果をCIの代用にしない。

## 本番への適用順序と旧Worker対策

1. `0035_source_movie_identity.sql` を適用する（この時点ではDB強制チェックは無効）。
2. 出典付きの確認カタログをインポートし、新しいWorkerをデプロイする。
3. 次のSQLでDB側の検証必須ポリシーを有効化する。

```sql
UPDATE movie_ingestion_policy SET require_source_identity=1 WHERE id=1;
```

有効化後は、取得元ID・表記・登録済みの識別情報を持たない新規上映、または未解決の保留表記の書き込みをDBが拒否する。誤って古いWorkerが再デプロイされても短縮名の登録を許可しない。日付差し替えはD1 batchのトランザクションなので、拒否時は削除を含むバッチ全体が戻り、既存データが残る。

このエラーが出た場合は最新の収集処理を含むコードへ戻す。ポリシーを無効化して古い収集処理を動かすことを恒久対策にしない。PagesなどからDBに直接上映を追加する新しい経路も、この識別情報と検証を通すこと。
